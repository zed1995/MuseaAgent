## Architecture

FastAPI photo search service with PostgreSQL/pgvector. Python 3.14, managed via `uv`.

### Package layout

```
backend/
  main.py           — FastAPI app entrypoint (create_app())
  app.py            — App factory
  api/              — HTTP layer (router + routes/health.py)
  core/             — Config, DB engine, ID generator, settings models
  models/           — SQLAlchemy ORM models (persistence objects only, never leave this layer)
  repositories/     — Data access: records, write models, repo implementations, UoW
  services/         — Placeholder for business logic
  schemas/          — Placeholder for Pydantic API schemas
  agents/           — Placeholder for agent orchestration
tests/
  unit/             — Fast, no DB needed
  integration/      — Require PostgreSQL + pgvector
```

### Persistence layer contract (strict, not soft)

There is a strict three-layer boundary:

1. **ORM models** (`backend/models/`) — SQLAlchemy `DeclarativeBase` subclasses. Map 1:1 to database tables. **Never exposed outside the persistence layer.**

2. **Repository records / write models** (`backend/repositories/records.py`, `write_models.py`) — `@dataclass(slots=True)` DTOs. Records are read-only return types; write models carry data into repositories.

3. **Repositories** (`backend/repositories/`) — Accept a session in the constructor. Own query construction. Return records, never ORM instances. Do NOT call `commit()` — that's the caller's responsibility.

### Transaction boundaries

`SqlAlchemyUnitOfWork` (context manager) coordinates multi-repository operations:
- Enters: creates session, wires all 4 repositories (`photo_indexes`, `conversations`, `messages`, `search_logs`)
- On commit: flushes all pending changes
- On exception: rolls back
- On exit: closes session

### ID generation

All primary keys are Snowflake-style BIGINTs generated by `IdGenerator(machine_id)` in the application layer. No DB sequences.

### Database schema (Alembic migration)

4 tables created by the initial migration `20260523_0001`:
- **photo_index** — retrieval index with `Vector(1536)` embedding, FTS on English `search_text`, lifecycle status
- **conversations** — conversation container (id, user_id, title, message_count, timestamps)
- **messages** — ordered messages per conversation (conv_id FK, role, content, JSONB structured_data/metadata)
- **search_logs** — coarse-grained search debug/evaluation log with JSONB for intents, filters, retrieved IDs

Indexes: HNSW on embedding (cosine), GIN on search_text FTS, btree on unsplash_user_id, orientation, conv_id.

### Migration rules

- First migration is hand-written (not autogenerated)
- Alembic autogeneration (`make revision`) is fine for follow-ups but output must be reviewed
- Historical migrations are append-only after merge

### Configuration

Settings read from env vars prefixed with `MUSEA_AGENT_` via pydantic-settings. Key defaults:
- `MUSEA_AGENT_DATABASE__URL` → `postgresql+psycopg://postgres:postgres@localhost:5432/musea_agent`
- `MUSEA_AGENT_ENVIRONMENT` → `development`

### Commit workflow

When using superpowers workflows (executing-plans, subagent-driven-development, etc.):
- **Do NOT auto-commit** during implementation — stage changes only
- After all changes for a feature/fix are complete, pause and wait for user review and confirmation
- Once confirmed, squash all changes into **a single commit per feature or fix**
- Use a descriptive multi-line commit message summarizing what was built and why

### Integration tests

Marked `@pytest.mark.skip(reason="requires PostgreSQL with pgvector")`. To run them, start PostgreSQL with pgvector, create `musea_agent_test` DB, remove the skip marker, then run `.venv/bin/pytest tests/integration/`.
